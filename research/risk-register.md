# Cramline Platform Implementation Risk Register

**Scope.** This memo synthesizes the supplied iOS Screen Time, privacy/billing, and Android/Google Play research. It is an implementation and release-planning document, not an assertion that any entitlement, review outcome, or device behavior has already been obtained. “Blocker” means work that must be resolved with external approval, the exact release archive, or physical-device evidence before the affected release claim is made.

## Executive decision

Build the **native SwiftUI iOS/iPadOS app first**, with a minimum deployment target of **iOS/iPadOS 16.0**. The iOS core is feasible only when the Family Controls distribution capability is approved and provisioned for the host and every shipped Screen Time extension, and the emergency/recovery flow is proven on real hardware and TestFlight.

The Android product must be described and designed as a **manual companion**: guidance, reminders, or a best-effort interruption after a user-selected supported app opens. It must **not** claim a system shield, hard blocker, package suspension, foreground-app certainty, or equivalent enforcement parity with iOS. An optional AccessibilityService interruption beta is a separate, policy-gated experiment—not a prerequisite for the manual companion—and must fail open.

> Product claim boundary: iOS may use approved Screen Time mechanisms to shield selected tokens, but individual authorization is self-authentication, revocable, and does not create an unremovable hard lock. Android cannot truthfully market an equivalent system shield or hard blocker under the stated consumer-app constraints.

## Confirmed implementation boundaries

| Area | What is supported or required | Non-negotiable product/engineering boundary |
|---|---|---|
| iOS authorization | `AuthorizationCenter.requestAuthorization(for: .individual)` is available on iOS/iPadOS 16+; `FamilyActivityPicker` produces opaque selections. | Individual authorization is self-authentication, revocable in Settings, and allows app deletion/iCloud sign-out. Adult-only is a product/terms constraint, not an Apple Family Controls age class. |
| iOS enforcement | ManagedSettings can shield selected app, web-domain, or category tokens. DeviceActivity supports recurring/one-off schedules and monitor extensions. | The documented `shield.applications` ceiling is **50 simultaneous application tokens**. Do not represent it as a picker-selection maximum, and do not promise the picker can prevent a 51st tap. DeviceActivity callbacks are not precision timers. |
| iOS sharing/extensions | App Groups are the documented host/extension shared-state mechanism. | Family Controls distribution approval and provisioning are needed for the host **and every Screen Time extension** used for TestFlight/App Store distribution. Keep telemetry SDKs/initialization out of extension targets; share only minimum opaque enforcement state through a restricted App Group. |
| iOS shields | Shield Configuration can present title/subtitle/icon and primary/secondary buttons; Shield Action has limited system responses, including `openParentalControlsApp`. | Shield configuration receives metadata for an actively shielded item. The defensible privacy rule is **do not retain or export it**, not “the app can never see a selected app name.” |
| Emergency pause | There is no native exact 15-minute pause primitive. | Clear Cramline shielding, best-effort schedule reapplication, and show an unknown/fail-open state when recovery cannot be verified. Never promise exact timing or irreversible enforcement. |
| Consent/telemetry | The free local core must work offline and with telemetry permanently declined. Firebase uses documented static Info.plist default-off controls before collection; Mixpanel must remain uninitialized before consent. | Runtime Firebase APIs still require initialization; “disable Firebase before native initialization” is imprecise. A zero Firebase-originated pre-consent collection claim is **unproven** until the exact pinned archive passes traffic testing and Firebase confirms behavior. |
| Purchases | StoreKit 2 supports verified transactions, current entitlements, a long-lived transaction-update listener, and user-initiated restore via `AppStore.sync()`. | Premium can cover ongoing AI/planning value only. Do not monetize shielding, emergency exits, core scheduling, deletion, or the free local core. |
| Android package and usage access | A finite `<queries>` list may be used only for a named supported-package installed check. | Do not use `QUERY_ALL_PACKAGES`, `PACKAGE_USAGE_STATS`, UsageStats foreground detection, or consumer-app `DevicePolicyManager` package suspension (requires enterprise device/profile-owner DPC). |
| Android AccessibilityService | If tested, filter service events to a local allowlist through `AccessibilityServiceInfo.packageNames` and minimum event types only during an active session. | The service needs the Play non-accessibility-tool declaration, separate prominent in-app disclosure, affirmative consent, listing disclosure, review video, and exact-beta-binary review. It is not an accessibility tool. |
| Android interruption UX | `TYPE_WINDOW_STATE_CHANGED` is only a best-effort UI-change trigger. | Never inspect event text, nodes, records, or window trees; hard-code `canRetrieveWindowContent=false` in XML. Disabled/ambiguous/missed events, card failure, restart, OEM battery behavior, and accessibility-service conflicts must all fail open without a false “protected/blocked” state. |

## Prioritized build recommendations

### P0 — Set the product contract and architecture before feature work

1. **Write platform-specific claims into product requirements and UI copy.** iOS: Screen Time shielding subject to authorization, revocation, and recovery limits. Android: manual guidance/reminder, with any AccessibilityService explicitly framed as a best-effort, fail-open interruption beta. Prohibit “hard blocker,” “system shield,” “unremovable,” “exact 15 minutes,” “always protected,” and Android parity claims.
2. **Set iOS/iPadOS 16.0 as the minimum and create separate SwiftUI targets** for the host, Device Activity monitor, Shield Configuration, and Shield Action extensions. Configure a restricted App Group for minimum opaque enforcement state only.
3. **Start the Family Controls capability request and provisioning plan immediately.** Make entitlement approval for every shipped target an explicit critical-path dependency rather than a late release task.
4. **Define a consent-first, offline-first data contract.** The free local core must operate with permanent telemetry decline. Keep telemetry SDKs out of extensions. Use Firebase documented static default-off controls before collection, leave Mixpanel uninitialized until consent, and do not publish zero-pre-consent-collection or literal-event-allowlist promises until exact-version testing supports them.
5. **Lock the monetization boundary.** Implement StoreKit 2 verification/entitlements/update listener/Restore Purchases, but reserve premium only for ongoing AI/planning value; no enforcement, emergency, deletion, core schedule, offline use, or restore paywall.

### P1 — Prove one safe iOS enforcement vertical slice on real devices

1. Implement individual authorization, opaque picker capture, shield application, DeviceActivity monitoring, and shield UI/action extensions.
2. Make the 50-simultaneous-app-shield ceiling visible in the enforcement flow without claiming the stock picker itself stops selection 51. Avoid default preselection and app/category identity classification.
3. Implement emergency pause as: clear Cramline shielding → best-effort reapply scheduling → recovery verification where possible → conspicuous unknown/fail-open state if not verified. Include emergency end and deletion in the free local core.
4. Test on physical iPhone/iPad, then TestFlight with the entitlement-bearing release archive. Test authorization revocation, app deletion/sign-out implications, over-limit state, restart, emergency recovery, schedule behavior, and extension communication.

### P2 — Make privacy, billing, and release evidence first-class deliverables

1. Pin all Firebase/Mixpanel/Crashlytics versions and audit target linkage. Validate static default-off configuration, no Mixpanel initialization before consent, post-consent disabled automatic behaviors specified in the research, opt-out queue purges, and extension network silence.
2. Capture release-archive traffic and inventory actual events/egress. Use this evidence to resolve the Firebase pre-consent uncertainty, automatic-event issue, Mixpanel `$opt_in` exception, and Crashlytics next-run limitation. Update privacy manifests and App Store privacy answers from what is actually observed.
3. Build automated/manual evidence packs: consent transition and queue-purge tests, StoreKit purchase/restore/update tests, static extension-dependency checks, App Group state review, and real-device emergency evidence. Add explanatory review notes for non-obvious features. A reviewer video is useful release evidence but is **not asserted here as an Apple TestFlight/App Store mandatory requirement**.

### P3 — Ship Android manual companion independently of AccessibilityService

1. Build manual planning/guidance/reminder flows that do not need `QUERY_ALL_PACKAGES`, Usage Access, DevicePolicyManager suspension, or AccessibilityService. Use finite `<queries>` only for a necessary named supported-package installed check.
2. Create Android-specific listing/onboarding assets stating manual guidance or a reminder/interruption after selected supported apps open. Do not reuse iOS “shield” or “app blocker” language.
3. If interruption has product value, run it as a separately gated beta: finite local package allowlist in `AccessibilityServiceInfo.packageNames`, minimum event type only during active session, hard-coded `canRetrieveWindowContent=false`, no inspection of text/nodes/records/window trees, non-coercive UX, and fail-open status.
4. Submit only the exact beta binary with the required non-tool declaration, prominent consent disclosure, listing disclosure, and review video. Do not distribute the feature based on assumed pre-approval. Validate TalkBack/other service coexistence, OEM battery/restart behavior, ambiguous/missed events, and no event/content leakage on physical devices.

## Disagreement and uncertainty ledger

| Topic | Supplied research position | Synthesis decision |
|---|---|---|
| Apple reviewer video | The iOS research corrects the claim that a reviewer video is mandatory: Apple review guidance requires explanatory notes for non-obvious features, not a stated mandatory reviewer video for TestFlight/App Store. The privacy/billing research includes reviewer video/instructions in its recommended release evidence packet. | Preserve both: include a video/instructions as prudent evidence where helpful, but do **not** call it an Apple-mandated iOS/TestFlight requirement. Android AccessibilityService review video remains an explicitly required gate in the supplied Android research. |
| “Disable Firebase before initialization” | Privacy research says literal pre-initialization disabling is imprecise because runtime Firebase APIs need initialization; documented pre-collection control is static Info.plist default-off configuration. | Use static default-off controls before collection; do not communicate an inaccurate runtime-initialization claim. |
| Strict telemetry allowlist | Firebase Analytics automatic events conflict with a literal manual-event allowlist; Mixpanel `optInTracking` produces `$opt_in`. | Do not promise literal allowlisting unless the exact pinned configuration proves it. Explicitly resolve `$opt_in` or use a validated alternative. |
| Immediate telemetry withdrawal | The desired immediate opt-out conflicts with transmitting a disabled-consent event and Crashlytics’ next-run effect. | Keep withdrawal evidence locally, purge queues, document the next-run Crashlytics limitation, and do not promise an unconditional immediate current-process guarantee. |
| iOS privacy exposure | Opaque picker tokens limit app identity use, while Shield Configuration can receive metadata for an actively shielded item. | Do not overstate opacity as “never sees app name”; enforce no retention/export of shield metadata. |
